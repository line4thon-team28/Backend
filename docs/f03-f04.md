# 공고 수집과 이미지 매칭

Spring은 수집·작업 상태·후보·소유권을 관리하고, Python은 사진 한 장의 벡터만 만듭니다. 공공데이터 API와 다운로드한 공개 모델을 사용하며 유료 추론 API는 호출하지 않습니다.

## 실행

1. [임베딩 서비스](../embedding-service/README.md)의 설치·모델 다운로드를 마친 뒤 실행합니다.
2. `.env.example`을 참고해 `PUBLIC_DATA_SERVICE_KEY`(Decoding), `EMBEDDING_API_KEY`를 로컬 `.env`에 넣습니다. Python 프로세스에도 동일한 `EMBEDDING_API_KEY`를 설정합니다.
3. `MATCHING_IMAGE_HOSTS`에 팀 S3 버킷의 정확한 호스트를 추가합니다. 기본 허용 호스트는 `www.animal.go.kr`, `openapi.animal.go.kr`이며 리다이렉트·사설 IP·임의 포트는 허용하지 않습니다. 공식 사진 서버가 `application/octet-stream`으로 내려주는 경우도 받아 실제 이미지 형식은 Python에서 검사합니다. 서명 URL은 만료되므로 작업 재시도 기간에도 접근 가능한 서버 발급 URL을 전달해야 합니다.
4. `PUBLIC_DATA_COLLECTION_ENABLED=true`, `MATCHING_WORKER_ENABLED=true`로 켜고 Spring을 실행합니다. 기본값은 외부 호출을 하지 않는 `false`입니다.

배포 작업은 포함하지 않습니다. 기존 `local` 프로필은 H2 메모리 DB이므로 종료하면 작업 기록도 사라집니다. 재시작 복구는 영속 PostgreSQL을 사용하는 `prod` 환경에서 적용됩니다. 비밀값을 Git이나 Swagger 예시에 넣지 않습니다.

## F-03 수집

- 공식 [구조동물 조회 v2](https://www.data.go.kr/data/15098931/openapi.do)를 사용합니다. 최초 최근 30일은 구조일 `bgnde/endde`, 이후는 수정일 `bgupd/enupd`이며 하루를 겹쳐 조회합니다.
- 종료된 공고도 갱신하기 위해 `state=notice`로 제한하지 않습니다. `desertionNo`가 upsert 식별자입니다. 공고번호 `noticeNo`와 구분합니다.
- 실제 확인한 응답의 사진 필드는 `popfile1`, `popfile2`입니다. 첫 버전은 공고 대표 사진 `popfile1`을 사용하고, 기존 `popfile` 응답도 처리합니다.
- 응답의 `orgNm`에서 시도를 구하고, `sigungu_v2`의 `orgdownNm/orgCd`로 시군구 코드를 보완합니다. 추측한 코드는 저장하지 않습니다.
- 30분 간격, 일일 요청 수 9,000회부터 2시간 간격, 10,000회에서 다음 날까지 중단합니다. 이 값은 개발계정 기본 예산이며 실제 발급 한도가 다르면 `pawpose.collection` 설정을 조정합니다.
- 외부 HTTP 호출은 DB 트랜잭션 밖에서 실행합니다. 페이지별 저장과 매칭 입력 등록은 같은 짧은 트랜잭션입니다. 전체 페이지 성공 때만 진행 날짜를 갱신하고, 중간 실패 시 이미 저장한 페이지는 다음 실행에서 중복 갱신합니다.
- 타임아웃·5xx는 최대 3회 재시도합니다. 수집 lease와 요청 횟수는 DB에 기록하므로 서버가 중단돼도 복구합니다. 여러 서버가 떠도 같은 lease를 동시에 처리하지 않습니다.

## 다른 기능에서 연결할 서비스

`MatchingInputService`는 내부 서비스입니다. 사진 URL을 임의로 받는 공개 매칭 등록 API는 추가하지 않았습니다. 각 등록 담당자가 업로드와 권한 검사를 끝낸 뒤 **등록 저장 트랜잭션 안에서** 호출합니다.

```java
// F-02: LostPet 저장 직후. 여러 사진을 모두 비교합니다(최대 5장).
matchingInputService.registerLostPet(savedLostPet.getId(), new MatchingProfile(
    photoUrls, lostDate, sidoCode, sigunguCode, breed, color, place));

// F-06: Sighting 저장 직후. 최대 3장; 사진은 JPEG/PNG로 변환해 전달합니다.
matchingInputService.registerSighting(savedSightingId, species, new MatchingProfile(
    photoUrls, sightedDate, sidoCode, sigunguCode, breed, color, place));

// F-08: 직접 상태만 바꾸지 않고 같은 행 잠금을 사용하는 경로로 처리합니다.
matchingInputService.markFound(authenticatedUserId, lostPetId);
```

위 예시는 호출 규격이며 아직 없는 F-02/F-06/F-08 Controller를 구현했다는 뜻이 아닙니다. `LostPet`에는 찾음 전환 메서드와 잠금 조회만 추가했습니다. 공고 입력은 `NoticeCollectedEvent`의 BEFORE_COMMIT 리스너가 자동으로 연결합니다.

새 실종 등록은 기존 보호소·목격 후보와 비교합니다. 새 공고·목격 사진 분석이 끝나면 찾는 중인 실종 등록을 다시 대기열에 넣습니다. 변경된 사진은 새로 분석합니다. 모델·전처리 버전이 다른 벡터는 비교하지 않습니다.

수집과 매칭 스케줄러는 별도 스레드에서 실행합니다. 실종 등록과 목격 제보 작업을 보호소 사진 일괄 분석보다 먼저 처리합니다. 다만 CPU로 전국 초기 사진을 모두 분석하는 데는 시간이 걸립니다. 등록 API는 분석을 기다리지 않고 상태를 반환하며, 전체 사진 분석이나 최초 후보 생성이 3초 안에 끝난다고 보장하지 않습니다. 모델 버전을 바꾸면 완료된 구버전 작업도 다시 대기 상태로 전환합니다.

작업은 `PENDING → PROCESSING → READY`로 진행합니다. 일시 실패는 지연 재시도 후 `FAILED`, 30분 뒤 다시 시도합니다. 잘못된 사진·허용되지 않은 호스트·모델 불일치 등 영구 오류는 자동 반복하지 않고 수동 재시도 또는 입력 수정을 기다립니다. 15분 이상 끝나지 않은 작업은 lease를 회수합니다. 이전 입력이나 이전 작업의 늦은 응답은 generation/token 검사로 폐기합니다.

## F-04 API

`GET /api/v1/lost-pets/{lostPetId}/matches?sort=similarity&page=0&size=20`

- 로그인 필수, 본인 등록만 조회합니다. `sort`는 `similarity` 또는 `deadline`, `size`는 1~20입니다.
- YES 후보 우선, NO 제외. 동률이면 match ID로 순서를 고정합니다. 마감임박순에서 마감일 없는 목격 후보는 뒤에 배치합니다.
- 선택한 정렬의 상위 20건 안에서 페이지를 나눕니다. `totalCount`도 최대 20입니다. 종료된 보호소 공고는 제외합니다.
- 같은 종, 실종일 이후, 같은 시도 또는 인접 시도를 비교합니다. 보호소 공고는 실제 구조일(`happenDt`)을 우선 사용하고, 누락된 경우만 공고 시작일을 사용합니다. 공고 시작이 늦었다는 이유로 실종 이전에 구조된 동물을 포함하지 않습니다. 여러 사진의 코사인 유사도 최댓값에 품종 +0.05, 털색 키워드 +0.03, 같은 시군구 +0.03을 더하고 0~1로 제한합니다. 초기 임계값은 0.60입니다.
- 후보를 재계산해도 기존 피드백은 보존하고 같은 조합을 중복 저장하지 않습니다. raw 점수와 모델 버전도 저장합니다. 표시 점수는 **동일 동물일 확률이 아닙니다**.

```json
{
  "data": {
    "items": [], "page": 0, "size": 20, "totalCount": 0,
    "processingStatus": "PENDING", "processingMessage": "사진 분석 중이에요",
    "failureCode": null, "retryAfterSeconds": 10, "scoreIsProbability": false,
    "pendingTargetCount": 0, "failedTargetCount": 0
  },
  "message": null
}
```

`READY`이면서 빈 목록일 때만 비교 완료·후보 없음을 표시합니다. 내 사진이 완료됐더라도 비교 조건에 맞는 공고·목격 사진이 대기 중이면 `PROCESSING`을 반환합니다. `PENDING/PROCESSING`이면 10초 후 다시 조회합니다. 대상 사진 일부가 실패했으면 `PARTIAL`과 `failedTargetCount`를 반환하며, 확인된 후보는 보여주되 전체 비교가 끝났다고 표시하지 않습니다. 내 사진 자체가 `FAILED`이면 실패 안내를 표시하고 `POST /api/v1/lost-pets/{lostPetId}/matches/retry`로 재시도할 수 있습니다(202). `NOT_REQUESTED`는 등록 담당자의 연결 호출 전, `CANCELLED`는 찾음 처리 후입니다. API 상세는 Swagger에 포함됩니다.

## F-09 연결

새 후보와 `matching_notification_outbox`를 같은 트랜잭션에 저장합니다. `match_id` unique 제약으로 재처리 알림을 막습니다. F-09는 `CandidateNotificationRepository.findByDeliveredFalseOrderById(Pageable)`를 읽고, 자신의 알림 행 저장과 `markDelivered()`를 **같은 트랜잭션**에서 처리하면 됩니다. 여러 소비자가 동작한다면 F-09 알림 테이블에도 match ID unique 제약 또는 행 잠금이 필요합니다. 찾음 상태에서는 새 outbox를 만들지 않습니다. 이미 생성된 알림의 조회·읽음 API는 F-09 담당 범위입니다.

## DB 변경과 확인

- 추가 테이블: `notice_collection_state`, `matching_source`, `matching_notification_outbox`.
- `notice`: 지역 코드·수집 시각·원본 fingerprint 추가.
- `matches`: 후보 활성 여부·raw 점수·모델 버전, `(lost_pet_id, notice_id)`와 `(lost_pet_id, sighting_id)` unique 제약 추가. `@DynamicUpdate`로 점수 변경이 피드백 컬럼을 덮어쓰지 않게 합니다.
- 기존 `ddl-auto:update` 방식을 유지합니다. 이미 후보가 있는 DB는 아래 중복 확인 후 적용해야 합니다. 중복 데이터를 자동 삭제하지 않습니다.

```sql
select lost_pet_id, notice_id, count(*) from matches
where notice_id is not null group by lost_pet_id, notice_id having count(*) > 1;
select lost_pet_id, sighting_id, count(*) from matches
where sighting_id is not null group by lost_pet_id, sighting_id having count(*) > 1;
```

## 검증과 남은 범위

`./gradlew test bootJar`, `cd embedding-service && python -m unittest discover -s tests -v`로 자동 테스트를 실행합니다. 실제 외부 호출은 기본 테스트에서 제외하며 `PAWPOSE_LIVE_TEST=true`, 공공 API 키, 실행 중인 임베딩 서비스가 있을 때 `LiveMatchingSmokeTest`를 선택 실행합니다.

일반 이미지 모델이 동물 개체를 정확히 구별하는지는 별도 평가가 필요합니다. 실제 동물 정답 사진 10건 중 top-5 8건이라는 품질 기준은 모델 추론 성공이나 합성 이미지 테스트만으로 충족했다고 볼 수 없습니다. 초기 60점 기준도 동물 사진 평가 전의 설정값입니다. S3 업로드, HEIC 변환, 등록·알림 API 전체와 실제 배포는 해당 담당자의 후속 연동 범위입니다.
